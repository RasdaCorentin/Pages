De VaporMap "prod Linux" à VaporMap "prod Docker"

Page d'introduction — resitue le lab de l'an dernier avant de passer au compte-rendu Docker.

Cette page ne redécrit pas le déploiement Docker en détail — c'est le rôle de index.html. Elle sert de pont : qu'avions-nous déjà construit, qu'est-ce qui change, et pourquoi repartir de cette base plutôt que de tout refaire.

Le lab de l'an dernier, avec M. Braux

Le lab "prod Linux" (Emmanuel Braux, cursus Administration Système) demandait de déployer VaporMap en production sur une VM Debian, sans conteneurs : installation manuelle des paquets, création d'un utilisateur système dédié, base MariaDB locale, API servie par Gunicorn, frontend par Nginx, le tout orchestré par systemd. Le compte-rendu de ce lab a été noté 14/20 (voir l'analyse détaillée).

Deux parties du sujet n'avaient pas été traitées à l'époque :

  • Partie 8 — activation des logs Gunicorn (--access-logfile / --error-logfile) vers /var/log/vapormap.
  • Partie 9 — point d'accès unique : faire passer l'API derrière Nginx (location /api/ en reverse proxy) au lieu d'exposer le port 5000 directement.

Ce qui reste valable

Le passage à Docker ne remet pas en cause l'architecture validée l'an dernier — il change la façon de la mettre en œuvre. Les mêmes briques sont réutilisées telles quelles :

Nginx devant les fichiers statiquesMême rôle : servir le frontend, gérer le cache. Seule la manière d'écrire config.json change (généré au démarrage du conteneur plutôt qu'à l'installation).
Gunicorn multi-workersMême commande de lancement (gunicorn wsgi:app), même rôle de serveur WSGI de production face au serveur intégré de Flask.
MariaDB séparée de l'APIDéjà le cas l'an dernier (base locale sur la VM, mais processus distinct). Le conteneur ne fait que rendre cette séparation plus stricte, avec un stockage explicitement externalisé (volume nommé).
Utilisateur non privilégiéapp-vapormap côté Linux devient l'utilisateur d'exécution défini dans le Dockerfile — même principe : le processus applicatif ne doit pas pouvoir modifier son propre code ni agir en root.
Migrations idempotentesflask db upgrade était déjà rejouable l'an dernier ; c'est cette propriété qui permet aujourd'hui de l'exécuter automatiquement à chaque démarrage du conteneur, sans intervention manuelle.

Les deux manques identifiés : où en est-on cette fois

Utile à savoir avant de lire le compte-rendu Docker : ces deux points n'étaient pas de simples oublis isolés, ce sont des sujets qui se posent différemment une fois en conteneur.

Manque (lab Linux)Statut dans le lab Docker
Logs Gunicorn non redirigés vers des fichiers dédiés Traité — mais différemment : en conteneur, on n'écrit pas de fichier de log (il disparaîtrait avec le conteneur). Les logs vont sur la sortie standard, collectée par docker compose logs. Le besoin d'origine (pouvoir consulter les logs) est couvert par un mécanisme plus adapté au contexte, pas par la solution initialement prévue.
Pas de point d'accès unique (API exposée directement sur le port 5000) Toujours ouvert — le port de l'API reste publié tel quel dans docker-compose.yml. C'est explicitement noté hors périmètre du lab Docker actuel (voir les "Compléments" du compte-rendu) : le reverse proxy Nginx → API n'est pas encore mis en place.
