Partie 1 — Définition des contraintes du mode "production"

Point de départ : le déploiement Docker en mode "développement" — frontend servi par http.server, API sur le serveur intégré de Flask, données SQLite dans le conteneur de l'API, images en root, code cloné sur la branche courante. Pour chaque point : le besoin, puis la solution. La colonne "Conteneurs" indique ce que Docker change par rapport au lab Linux précédent : Résolu par la technologie, À traiter malgré elle, ou Nouveau.

L'exploitant agit sur tous les composants côté serveur (déploiement, paramètres, sauvegarde) ; il n'a pas de flux applicatif propre.

Workflows

Affichage de la carte et des points
  1. Le navigateur demande / au serveur de fichiers statiques, puis les scripts et feuilles de style.
  2. Il demande config.json et y lit l'adresse de l'API.
  3. Il demande les tuiles au fournisseur de cartes.
  4. Il envoie GET /api/tracks/ à l'API, qui lit les points en base et renvoie un GeoJSON.
  5. L'application cliente affiche les points sur la carte.
Saisie d'un point
  1. L'utilisateur remplit le formulaire.
  2. Le navigateur envoie POST /api/points/ à l'API.
  3. L'API valide les données, puis les enregistre en base (erreurs par champ sinon).
  4. Le navigateur relance GET /api/tracks/ pour rafraîchir la carte.

La suppression suit le même principe (DELETE) : l'URL du point est construite par l'API, et c'est le navigateur qui l'appelle — l'API doit donc connaître l'adresse sous laquelle le navigateur la joint.

Ce qui change par rapport au mode "développement"

Partie 4 — Développement des images des services

db : image existante

Aucune image n'est développée : mariadb:11.4.13 (branche LTS 11.4, version précise) couvre tous les besoins.

api — Image de base : python:3.12.14-slim-trixie

Écart avec l'environnement validéMême version de Python. Distribution différente (Debian 13 vs Ubuntu 24.04), mais mêmes familles de paquets
Contenu inutileFaible : variante slim
À ajouterCompilateur + en-têtes MariaDB pour mysqlclient (build), libmariadb3 (exécution)
Origine / mise à jourImage officielle Docker, reconstruite à chaque correctif Python/Debian

Écartées : ubuntu:24.04 (Python "externally managed", pas de suivi correctif) et python:3.12-alpine (musl → pas de roues précompilées, comportement différent).

Choix de mise en œuvre — api

  • Code figé : ADD https://gitlab.com/vapormap/vapormap-api.git#<commit> — BuildKit clone lui-même, git n'est pas installé, .git non copié. Le commit est un ARG.
  • Découpage en couches : installation des outils de build, compilation de mysqlclient et suppression dans un seul RUN — sinon les outils resteraient dans la couche qui les a installés. libmariadb3 installé explicitement, sinon apt-get --auto-remove le supprimerait avec libmariadb-dev.
  • wheel non installé séparément : pip récent construit dans un environnement isolé qui installe ses propres outils.
  • Pas de venv (voir Partie 3).
  • Identifiants de la base : aucun ENV VAPOR_DB* dans l'image — sans variables au lancement, l'API tenterait localhost (le conteneur lui-même) et échouerait.
  • Gunicorn configuré par GUNICORN_CMD_ARGS : workers/port changeables au lancement. --worker-tmp-dir=/dev/shm place le heartbeat en mémoire.
  • Initialisation : entrypoint.sh lance flask db upgrade puis exec "$@" (Gunicorn devient PID 1, reçoit directement SIGTERM). set -e arrête le conteneur si la migration échoue.
  • Utilisateur vapormap : code propriété de root, lu (pas modifié) par l'utilisateur d'exécution — fonctionne grâce à PYTHONDONTWRITEBYTECODE=1.
  • Documentation : LABEL org.opencontainers.image.authors, EXPOSE 5000 (métadonnée, ne publie rien — c'est ports: dans compose qui publie).

frontend — Image de base : nginxinc/nginx-unprivileged:1.30.5-alpine3.24

Écart avec l'environnement validéSans objet : fichiers statiques, indépendants de la distribution
Contenu inutileTrès faible : Alpine + nginx
À ajouterFichiers du frontend, script de génération de config.json (envsubst déjà présent)
Origine / mise à jourMaintenue par NGINX (F5), branche stable 1.30
UtilisateurTourne déjà en non-root (uid 101), droits déjà en place

Choix de mise en œuvre — frontend

  • Configuration nginx écrite dans le dépôt (pas de template) : port, server_name et racine sont propres à l'image, pas au déploiement.
  • config.json généré au démarrage : l'adresse de l'API dépend du poste utilisateur, elle ne peut pas être figée au build. Script placé dans /docker-entrypoint.d/, exécuté avant nginx — nginx reste PID 1.
  • Droits : seul config.json appartient à l'utilisateur 101 (seul fichier réécrit au démarrage).
  • Cache-Control: no-store sur config.json : évite qu'un navigateur garde l'ancienne adresse de l'API.

Partie 5 — Développement de la stack de l'application

Voir docker-compose.yml et .env.example.

Mise à disposition des images

Images construites localement par docker compose build, aucun registre disponible pour ce lab — le dépôt contient les Dockerfiles, le code est figé par commit : deux builds donnent le même résultat. En production réelle : build une fois, push dans un registre, le serveur ne ferait que pull.

Choix de mise en œuvre

  • Non redéclaré : réseau (compose en crée un par défaut), commandes de lancement, utilisateurs, ports internes, signaux d'arrêt — déjà définis dans les images.
  • Deux adresses de l'API : VAPOR_DBHOST: db (interne, DNS Docker, pour le conteneur API) vs VAPORMAP_BACKEND_HOST: ${VAPORMAP_PUBLIC_HOST} (publique, pour le navigateur — api n'aurait ici aucun sens).
  • Paramètres dans .env (non versionné), .env.example comme modèle.
  • Ports publiés : frontend (8000) et api (5000) seulement — pas db.
  • Volume db-data, monté sur /var/lib/mysql, survit à down mais pas à down --volumes.

Démarrage fiable

depends_on seul n'attend que le démarrage du conteneur de la base, pas qu'elle accepte des connexions — la migration de l'API échouait au premier lancement. Solution : healthcheck sur db (--connect + --innodb_initialized), API conditionnée par condition: service_healthy.

RéglageValeurEffet
interval5sL'API démarre au plus 5 s après que la base est prête
timeout3sUne connexion locale > 3 s signale un problème
start_period30sLes échecs pendant l'initialisation d'un volume vide ne sont pas comptés
retries525 s d'échecs consécutifs après start_period avant "unhealthy"

Limites : la vérification n'a lieu qu'au démarrage — si la base tombe ensuite, l'API n'est pas relancée (pool_pre_ping aide à reprendre la connexion). Si la base reste unhealthy, docker compose up échoue plutôt que d'attendre indéfiniment.

Procédure

cp .env.example .env     # puis modifier VAPOR_DBPASS
docker compose build
docker compose up -d
docker compose ps

Partie 6 — Validation du bon fonctionnement de l'application

Ouvrir http://localhost:8000, créer deux points. Dans l'onglet Réseau, vérifier que les requêtes vers http://localhost:5000/api/tracks/ et /api/points/ partent du navigateur, avec un statut 200 ou 201.

docker compose ps --format 'table {{.Service}}\t{{.Ports}}'

# db n'est pas joignable depuis l'hôte
nc -zv localhost 3306
# db est joignable depuis la stack
docker compose exec api python -c "import socket; socket.create_connection(('db', 3306), 2); print('db OK')"

Attendu : ports publiés pour frontend et api uniquement.

docker compose top

Attendu : vapormap (Gunicorn), 101 (workers/master nginx), mysql uid 999 (MariaDB).

docker compose exec db mariadb -u user_vapormap -p db_vapormap -e 'SELECT * FROM point;'
docker compose exec api find / -name '*.db' -o -name '*.sqlite*' 2>/dev/null

docker compose down
docker compose up -d
docker compose exec db mariadb -u user_vapormap -p db_vapormap -e 'SELECT * FROM point;'
docker compose logs frontend
docker compose logs api
docker compose logs db
# aucun fichier de log écrit dans les conteneurs
docker compose exec frontend ls -l /var/log/nginx/
docker compose down --volumes
docker compose up -d
docker compose ps       # tous "running", db "healthy"

time docker compose stop frontend
time docker compose stop api
time docker compose stop db
docker compose logs --tail 5 frontend api db

Attendu : arrêt en moins d'une seconde pour les trois services — le processus qui reçoit le signal est le serveur lui-même (nginx, Gunicorn grâce à exec, MariaDB). Un arrêt proche de 10 s indiquerait un conteneur tué à l'expiration du délai de grâce.
